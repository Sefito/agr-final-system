# Step-by-step delivery sequence

Status: proposed order. This documentation iteration completes analysis only; implementation and live acceptance are pending.

## 1. Establish ownership and policy

Read module READMEs and confirm the initial CRM/use cases, simple file formats and upload destination. Resolve identity authority and authorization topology before exposing a real deployment. Keep tenant/user identity and scope explicit in every protected contract.

Output: agreed use-case contracts and policy decisions, not an engine choice inferred from folder names.

## 2. Define the first document slice

Specify browse/upload/download and original/occurrence/version identity. Decide upload readiness and staging lifecycle. Select a new migration baseline and typed persistence conventions. Describe the transaction shared by bytes, domain records and applicable receipts.

Output: a reviewable API/event and data lifecycle contract. No wholesale legacy schema or synthetic CRM funnel copy is assumed.

## 3. Prove one commercial approval slice

Compare explicit proposal/approval commands with a suitable durable runtime for a complete draft/edit/save path. Measure adaptation code and recovery under crash, duplicate approval, changed evidence, revoked permission, browser loss and deployment-version change.

Output: one selected execution approach and a compatibility/recovery contract. Do not maintain parallel engines in production.

## 4. Implement shared commands and frontend flows

UI and agent use the same typed use cases. Build authorized explorer, proposal review and the first agreed CRM forms. Generate HTTP types and separately maintain streaming schemas. Use explicit production unavailable states.

Output: one coherent vertical slice with meaningful synthetic unit, contract and integration verification.

## 5. Establish one customer-local Azure deployment

Use reviewed Bicep and explicit customer bootstrap; wire real Entra identity and runtime grants. Add scoped federated releases and optional Lighthouse operations separately. Select resource sizes using measured workload rather than the earlier hypothetical price table.

Output: synthetic staging deployment evidence, tested database restore, release/configuration digest and measured cost envelope. Live customer resources require explicit authorization.

## 6. Add the selected source connector

If SharePoint is chosen, confirm site grants, source-access mapping and deletion behavior. Demonstrate pagination, incremental reconciliation, metadata-only updates, rename/move and recovery from cursor failure.

Output: reliable authorized source catalogue. Unsupported files remain visible when allowed; complex processing stays outside scope.

## 7. Migrate and evolve

Inventory which existing data/checkpoints must migrate. Preserve identities, originals, citations and receipts; reconcile results without destructive reseeding. Add later CRM entities or processing features only against agreed requirements.

Output: a rehearsed migration and rollback/recovery plan, with actual test evidence distinguished from the design documents.
