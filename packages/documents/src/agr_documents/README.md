# Documents and catalogue

Status: identity concepts and explorer scope selected; storage retention provisional.

## Responsibility

Own source hierarchy, file occurrences, original bytes, logical documents, versions, renditions, upload staging and publication. Expose authorized operations to the explorer, CRM, retrieval and commercial workflows.

## Decisions

- Preserve separate identities for content blob, occurrence, logical document, version and rendition. Equal hashes do not imply equal access.
- Use stable source/folder IDs and parent relationships. Names and paths can change without creating a different logical source.
- Filter folders, filenames, counts and downloads before returning metadata. Indexing status does not determine access.
- Keep authorized unsupported files visible with an explicit not-indexed status. Complex processing is outside initial scope.
- Provisionally store platform originals/generated bytes in PostgreSQL with a 25 MiB cap. The cap and archive-expansion limits are different checks.
- Uploaded originals and sanitized model representations are distinct artifacts with distinct disclosure rules.
- Drafts are not automatically searchable corpus material. Publication, not draft creation, changes the active published version.
- Proposed initial uploads belong to AGR. Optional SharePoint write-back needs its own source-of-truth decision.

## Use cases and boundaries

List folders/files; stage an upload; attach an authorized original; create a logical document/version; propose an edit base; commit a version; publish or discard; download an authorized rendition; register source changes/deletions.

Commercial coordinates approvals and generation. This module owns the resulting version/publication writes and concurrency checks. Retrieval owns derived index state. CRM owns project creation and relationships through explicit operations.

Version commands take the expected base version and an idempotency identity. A stale base produces a conflict; it never silently replaces a newer version. An approved proposal must remain bound to its actor, scope, content and evidence revision.

## Transaction and recovery

Preserve atomic platform bytes, version rows, citation links and associated business receipt where required. Participants in one commit share the caller's transaction; module methods do not independently commit it. Rendering/model calls happen outside long-held database locks, followed by final revalidation at commit.

Index enrichment can run later, but successful upload response semantics must specify whether authorized lexical evidence is already available. Do not silently replace the legacy ready-on-success behavior with eventual processing.

## Acceptance cases

Duplicate upload/approval does not create duplicate versions; failed commit leaves no partial publication; a draft leaves the previous published document active; revoked access prevents download; a renamed file retains identity; same bytes in two scopes remain separately authorized.

## Open decisions

Define folder creation/move permissions, retained-version policy, staging expiry, supported initial formats, source deletion effects on historical citations, and synchronous versus asynchronous upload readiness. Select malware inspection and safe archive handling during upload implementation; no scanning service is selected now.
